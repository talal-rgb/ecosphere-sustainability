# Render staging setup

This runbook provisions an isolated staging website, API, and PostgreSQL database from `render.yaml`. It does not alter the existing production service and does not require custom domains initially.

## Security boundary

- Do not copy production data into staging.
- Configure every secret in Render, the storage provider, or the identity/email provider dashboard. Never put secret values in Git, a PR, deployment logs, or ordinary chat.
- Keep the migration database credential separate from `DATABASE_URL`. The API runtime must use a non-owner role with `NOBYPASSRLS`.
- The Blueprint uses paid `starter` web service and `basic-256mb` PostgreSQL resources because free services sleep and free databases expire after 30 days. Creating the Blueprint can incur charges and therefore requires account-owner approval.

## Render access needed

For diagnosis only, grant a Render workspace role that can view service events and logs. In **Render Dashboard → workspace selector → Settings → Team members → Invite members**, invite the operator as **Developer**. Developer is sufficient for logs and service configuration in an unprotected environment; use **Admin** only if the staging environment must be created as protected or billing must be changed. Hobby workspaces do not support invitations, so the account owner must instead open the service and provide the non-secret configuration checklist below or upgrade the workspace.

Do not share a Render password, API key, deploy hook, database URL, or environment-variable values.

For the existing `terrnix-backend` service, open these pages and record only non-secret values:

1. **Settings → Build & Deploy**: repository, branch, root directory, runtime, build command, start command, auto-deploy mode, instance type, region, and health-check path.
2. **Deploys**: current live deploy SHA/status/time and the last failed deploy's failure stage. Do not copy log lines containing environment values or request payloads.
3. **Events / Logs**: filter the last 24 hours for start failures, out-of-memory exits, port binding, health-check failures, and request timeouts. Redact email addresses and tokens.

## Blueprint creation

1. Merge the reviewed staging PR to `main`.
2. In Render, choose **New → Blueprint** and connect `talal-rgb/ecosphere-sustainability`.
3. Select `render.yaml`, review the three resources, and confirm the paid resource cost before applying.
4. Keep the generated `onrender.com` URLs until the authenticated journey passes. Do not add `staging.terrnix.com` or `api-staging.terrnix.com` yet.
5. In `terrnix-staging-api → Environment`, enter the prompted values below. Render stores them as encrypted environment values; do not paste them into chat.

## Required API environment variables

| Variable | Configure in Render from | Enables |
|---|---|---|
| `DATABASE_URL` | Internal URL for a dedicated `terrnix_app_staging` PostgreSQL role with `NOBYPASSRLS`; never use the database owner URL | Authenticated platform and tenant RLS |
| `EVIDENCE_STORAGE_BUCKET` | Staging-only private S3-compatible bucket name | Evidence intake |
| `EVIDENCE_STORAGE_REGION` | Storage provider's bucket region | Request signing |
| `EVIDENCE_STORAGE_ENDPOINT` | Provider endpoint; for AWS S3 leave the value empty | S3-compatible storage |
| `AWS_ACCESS_KEY_ID` | Staging-only storage service account | Signed upload/head requests |
| `AWS_SECRET_ACCESS_KEY` | Same staging-only storage service account | Signed upload/head requests |
| `BREVO_API_KEY` | Brevo transactional sandbox/staging key | Verification and password-reset mail |
| `CONTACT_FROM_EMAIL` | Verified staging sender address | Transactional sender identity |
| `CONTACT_TO_EMAIL` | Staging test inbox | Operational test notifications |

`BETTER_AUTH_SECRET` is generated by Render. Do not replace or copy it unless rotating it deliberately; rotation invalidates existing sessions.

Optional integrations stay unset until their phase:

- Google OAuth: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.
- Microsoft OAuth: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT_ID`.
- SMTP fallback: `ZOHO_SMTP_HOST`, `ZOHO_SMTP_PORT`, `ZOHO_SMTP_USER`, `ZOHO_SMTP_PASS`.
- Stripe test mode only: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, plus a dedicated `BILLING_DATABASE_URL`.
- Document and report workers: `DOCUMENT_WORKER_DATABASE_URL`, `REPORT_WORKER_DATABASE_URL` using their separately granted roles.

## Database bootstrap

1. In `terrnix-staging-postgres → Info`, use the owner connection only in a secure shell or a temporary Render environment value named `MIGRATION_DATABASE_URL`.
2. Run `cd backend && npm ci && DATABASE_URL="$MIGRATION_DATABASE_URL" npm run db:migrate`. Do not echo either URL.
3. Create `terrnix_app_staging` with `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS` and apply the API grants in `backend/DEPLOYMENT.md`.
4. Put that role's internal connection URL in `terrnix-staging-api → Environment → DATABASE_URL`.
5. Delete `MIGRATION_DATABASE_URL` from the API service before starting it. The runtime must not retain owner credentials.
6. Verify the connected runtime role with `SELECT current_user, rolbypassrls FROM pg_roles WHERE rolname = current_user;`; it must report `false` for `rolbypassrls`.

After configuration, `/health` must report `environment: staging`, a resolvable `gitCommit` equal to the Render deploy SHA, and a fixed `buildDate`. Then run the persistent two-organization isolation journey before enabling OAuth or billing.
